## Accepted implementation

- The sole importer remains the frozen `utf8-plain-text-v1` profile with strict
  UTF-8, one optional leading BOM, exact CR/LF/CRLF topology and the unchanged
  byte, code-point, physical-line, line-length and segment limits.
- User paths remain confined to `FilesystemQuarantine`. A versioned,
  vault-scoped HMAC key is now mandatory; identical bytes remain duplicate-stable
  across a same-vault restart and unlinkable under a different vault key.
- Intake compares the opened handle through the complete read, including change
  time, and rechecks the path as a regular non-reparse object after open and after
  read. Same-size mutation, inspection/open replacement, Windows reparse state,
  directories, links and special files fail closed.
- The parser remains an untrusted proposal boundary. Application-owned
  reconstruction with the frozen standard-library parser certifies the complete
  immutable candidate, including all identities, counts, BOM/encoding metadata,
  transformations, segment ordering/ranges and physical-line topology.
- Incompatible signatures are evaluated against the semantic payload after the
  one permitted leading BOM is recognized. Every frozen signature is rejected
  both with and without that BOM.
- Preview and consent bind the exact resolved policy decision. The service reads
  accepted active `data_policies` and `policy_lineage`, includes exact own/parent
  versions and edges in the decision identity, requires every effective row to be
  `local_only` / `never_cloud`, and resolves again immediately before commit.
- Consent remains service-minted, object-identity-bound and single-use. Hostile
  imported instructions, URLs, HTML, Markdown and tool syntax remain inert data
  and cannot alter policy, mappings, consent, limits, E07, network or tools.
- Redacted content cannot be mapped as attributed verbatim evidence. Original
  bytes, exact segments, transformations and mapped records remain separate.
- Debug representations for quarantine, parser, preview, consent, canonical,
  commit, deletion and transformation values omit content, paths, replacements
  and protected or stable digest identities.

## Canonical storage and migration decision

The review classified the candidate's process-local `dict` / `set` / `list`
authority as `E08_CANONICAL_INTEGRATION_REQUIRED`. It was not accepted as an E03
or encrypted-storage implementation.

The repair adds schema version 5, `e08_untrusted_import_v5`, as the exact next
version under the repository's existing ordered migration convention. It is a
strictly additive V4-to-V5 delta with three tables:

- `e08_quarantine_objects` for governed exact bytes and protected fingerprint
  metadata inside the accepted encrypted database boundary;
- `e08_import_sources` for exact preview, consent, parser, profile, policy and
  correction bindings;
- `e08_import_nodes` for segment, transformation and mapping provenance required
  beyond the accepted E03 column shapes.

Accepted semantic rows are also written to `source_artifacts`,
`source_locators`, `reports` or `assertions`, and `record_relations`. The E08
tables supplement rather than reinterpret those canonical types. V1–V4 ordered
statements, inventories and checksums are unchanged. Established V4 vaults
require verified backup and logical export before V5; fresh V5 creation, atomic
rollback, no-op rerun, V4/V5 portability and governed-byte restore are tested.
No non-additive E03 semantic change or architecture deviation was required.

## Durable lifecycle and deletion

- Commit writes canonical rows, exact governed bytes, provenance and correction
  closure in one database transaction. The in-memory dictionaries are reloadable
  query caches, not authority, and the service no longer creates a default store.
- Reopening a V5 database reconstructs exact source bytes, source/segment
  locators, mapped records, correction state and relations. A recreated service
  can prepare and execute deletion without the original quarantine object.
- Correction writes a new immutable source/version, closes the old accepted
  source and all old descendants, clears their usable content and records a real
  accepted `corrects` edge.
- Deletion computes closure from persisted nodes and accepted relations. It
  deletes exclusive descendants and governed bytes, invalidates and clears mixed
  descendants, preserves unrelated branches, verifies accepted canonical and raw
  absence, and persists a content-free receipt in the same transaction.
- Injected faults at A–F — before mutation, after descendant mutation, before and
  after raw deletion, during verification and before receipt persistence — all
  roll back. Reopen proves no dangling or falsely completed state remains.
