## Implementation details

### Snapshot and bounded rollback evidence

- All schema tables are mandatory. Manifest `table_inventory`, manifest
  `table_checksums`, and decrypted payload keys must be identical to the exact
  frozen inventory and to each other.
- `schema_migrations` must contain exactly frozen V1 evidence; no checksum is
  fabricated during restore.
- The authenticated package sequence must equal the next value implied by the
  package's own `backup_manifests` history for that vault.
- No external persistent sequence floor exists in accepted E00 architecture.
  E01 therefore does not claim detection of a cryptographically valid older
  package presented in a fresh context with no trusted current-vault state.

### Restore and activation

- Restore uses a newly reserved, isolated path and never accepts the active
  vault as the candidate target.
- Validation executes accepted migration verification, exact table comparison,
  SQL constraints/FKs, canonical row equality, deletion-state equality and
  SQLCipher integrity before returning an activation candidate.
- Supported E01 activation is a checkpointed, sidecar-free database transition.
  Existing main/WAL/SHM bytes are included in fault evidence; activation rejects
  present WAL/SHM rather than silently mixing them with a new main file.
- Windows publication and activation use verified file handles and a verified
  destination-directory handle at the mutation point. Post-mutation checking is
  supplementary, not the prevention mechanism.

### Recovery lifecycle

- Recovery header is outside both the SQLCipher vault and encrypted backup.
- Backup creation fails if recovery material is found in `vault_config`.
- The recovery CLI rejects `--vmk-hex`; the database key is freshly derived
  from the recovered VMK and authenticated vault salt.
- Raw VMK, backup key and recovery secret are cleared best-effort and are absent
  from package, report and evidence.

## Residual E01 risks

1. Bounded rollback evidence has no external trusted monotonic floor; E01 makes
   no stronger anti-rollback claim.
2. Python secret zeroization remains best-effort.
3. Administrator/SYSTEM, hostile kernel/filesystem drivers, and arbitrary code
   execution in the trusted process are outside the E01 Windows boundary.
4. Independent human crypto/privacy/recovery review is still required before
   any future REAL_DATA_GATE consideration.
