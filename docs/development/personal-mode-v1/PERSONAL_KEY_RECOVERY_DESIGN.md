# Personal key, recovery, and database-rotation design

Status: **ACCEPTED**. Design IDs: `PMV1-KEY-ENVELOPE-V1`, `PMV1-ROTATION-ISOLATED-REENCRYPTION-V1`, and `PMV1-RECOVERY-BOOTSTRAP-V1`. Implementation was completed and merged under the historical authorization recorded in [IMPLEMENTATION_AUTHORIZATION.md](IMPLEMENTATION_AUTHORIZATION.md); `REAL_DATA_GATE` remains **CLOSED**.

## Cryptographic profile and key versions

The existing algorithms are used unchanged: a 32-byte CSPRNG VMK, current-user DPAPI `OSKeyWrapper`, Argon2id/AES-256-GCM `RecoveryWrapper`, AES-256-GCM, and HKDF-SHA256 `derive_domain_key`. A key version is a positive bounded integer (`1..2^31-1`). For version `v`, the envelope holds fresh 32-byte `db_salt`, `backup_salt`, `export_salt`, and `manifest_salt`; `Kdb(v) = derive_domain_key(VMK(v), "database", db_salt(v))`, with equivalent existing literal domains for backup, export, and manifest. A retained version is read/recovery-only and is never supplied to an active-write connection.

`PMV1-KEY-ENVELOPE-V1` is one active key only. Its path is `%LOCALAPPDATA%\\PSYCHE OS\\Personal\\key-envelope.pmv1.json`; restrictive current-user ACLs apply to it and its parent. Canonical UTF-8 JSON is sorted keys and compact separators, with no BOM. Its exact fields are `format`, `version`, `vault_id`, `profile_id`, `profile_version`, `key_version`, `key_state` (`active` only), four `*_salt_hex` fields, `dpapi_vmk_hex`, and `recovery`. `recovery` is the exact existing `RecoveryWrapHeader` serialization. No unknown or duplicate fields, floats, noncanonical hex, unsupported versions, mismatched identifiers, or malformed headers are accepted. IDs are ASCII `[A-Za-z0-9_-]`, 1–128 bytes; every salt is exactly 64 lowercase hex characters; the DPAPI blob is 1–16 KiB; recovery ciphertext is 28–128 bytes; existing Argon2 bounds are time 1–10, memory 8192–262144 KiB, parallelism 1–8, and hash length 32. Parsing or unwrap failure is closed and never generates/replaces a VMK.

The active envelope contains only the current VMK wraps. Pending N+1 material is represented only in the authenticated rotation journal; old material is represented only by immutable retained envelopes. This prevents a single active file from ambiguously claiming two keys.

## Selected database transition

The sole Personal rotation primitive is **isolated SQLCipher re-encryption** (`PMV1-ROTATION-ISOLATED-REENCRYPTION-V1`). With the source opened under `Kdb(N)`, SQLCipher attaches a private same-volume staging database under `Kdb(N+1)` and copies through its native encrypted export primitive (`sqlcipher_export`); it then detaches and closes both databases. `PRAGMA rekey` is forbidden for Personal Mode.

Disposable synthetic proof using the repository runtime, SQLCipher **4.12.0 community**, showed both primitives: `PRAGMA rekey` made N+1 open and N fail after the operation, but changes the only active bytes in place. Native encrypted export produced a separate N+1 database, preserved rows and schema, returned `integrity_check=[('ok',)]` and `foreign_key_check=[]`, reopened under N+1, rejected N, and left N independently readable. No WAL or SHM remained after checkpoint/close. The proof used only temporary synthetic rows and deleted its directory. Interrupted in-place rekey has no independently verified N rollback byte, so it is not selected.

Before export, the service exclusively quiesces writers, checkpoints the N WAL (`TRUNCATE` or fail), closes external handles, and records that no `vault.sqlite-wal` or `vault.sqlite-shm` remains. It exports to `staging\\rotation-<uuid>\\candidate-N+1.sqlite`, opens that candidate only with Kdb(N+1), checks schema/inventory, semantic invariants, `integrity_check=ok`, `foreign_key_check=[]`, and a close/reopen. It never activates a candidate merely because its file exists.

## Durable artifacts and publication protocol

All names below are trusted fixed names below the Personal root; no renderer input controls them.

| Artifact | Exact path | Meaning |
|---|---|---|
| active envelope | `key-envelope.pmv1.json` | the sole active N envelope |
| rotation journal | `rotation-journal.pmv1.json` | the only pending N→N+1 transition |
| candidate DB | `staging\\rotation-<uuid>\\candidate-N+1.sqlite` | non-active, N+1 encrypted DB |
| replace backup | `staging\\rotation-<uuid>\\previous-N.sqlite` | old active bytes produced by activation; temporary recovery aid |
| retained envelope | `retained-keys\\key-envelope-v<N>.pmv1.json` | immutable N cryptographic identity and protected recovery material |
| retained lifecycle metadata | `retained-keys\\key-v<N>.pmv1.metadata.json` | authenticated content-free lifecycle state for that immutable envelope |

`PMV1-ROTATION-JOURNAL-V1` has at most 64 KiB. Its canonical top-level fields are exactly `format`, `version`, `vault_id`, `profile_id`, `profile_version`, `from_key_version`, `to_key_version`, `stage`, `created_at`, `candidate_id`, `auth_nonce_hex`, and `auth_ciphertext_hex`. `stage` is one of `prepared`, `candidate_verified`, `activation_started`, `db_n_plus_1_verified`, `retained_n_published`, `envelope_n_plus_1_promoted`, or `rotation_complete`. The authenticated ciphertext decrypts with `Kmanifest(N)` using existing AES-256-GCM. Its AAD is `PMV1-ROTATION-JOURNAL-V1|` followed by the canonical top-level object excluding `auth_nonce_hex` and `auth_ciphertext_hex`. Its exact plaintext object is `pending_envelope` (the fully parseable N+1 envelope, with `key_state: pending` only inside this object), `pending_envelope_sha256`, `old_envelope_sha256`, `active_db_identity` (`vault.sqlite`, expected vault/profile IDs), `candidate_db_relative_path`, `previous_db_relative_path`, `candidate_db_sha256`, and `candidate_schema_fingerprint`. Hex is lowercase; nonce is 12 bytes; ciphertext is bounded by the 64 KiB total; unknown/duplicate/missing fields, path traversal, identifier mismatch, digest mismatch, unauthenticated ciphertext, or an invalid stage fail closed. The journal contains no plaintext VMK, recovery secret, or plaintext database key. The protected pending envelope contains only DPAPI-wrapped and RecoveryWrapper-wrapped VMK(N+1).

Each staging file is created with restrictive ACL and no-replace semantics, flushed with `FlushFileBuffers`, and closed/reopened for validation. The journal and active/retained envelopes use write-private-sibling → flush file → atomic same-volume replace/no-replace → reopen/parse/verify. The implementation invokes directory flush where the platform exposes it; Windows does not provide a portable directory-sync promise, so every startup treats an absent/partial artifact as an explicit fault state and relies on the already durable predecessor/journal rather than assuming directory durability. Replacement activation uses the Windows same-volume replace primitive with write-through semantics to replace `vault.sqlite` by the verified candidate and preserve the old target as `previous-N.sqlite`; it never copies across volumes.

Ordered rotation publication is exact:

1. Verify active envelope N, DB N, recovery path, pre-rotation backup, capacity, and quiescence; generate N+1 only in memory.
2. Build and unwrap-verify the N+1 pending envelope, then write/flush/reopen the authenticated `prepared` journal. Active DB and active envelope remain N.
3. Export, checkpoint/close, hash, and fully reopen/verify the N+1 candidate; replace the journal with durable `candidate_verified`.
4. Replace the journal with durable `activation_started`, then replace `vault.sqlite` with the candidate using the write-through same-volume primitive. The journal still contains a recoverable N+1 envelope and N remains represented by the active envelope/previous bytes.
5. Reopen `vault.sqlite` with only Kdb(N+1), rerun the full checks, then replace the journal with `db_n_plus_1_verified`. No normal writes are allowed.
6. Before replacing the active envelope, publish the immutable retained N envelope with exactly the old protected VMK/salts, vault/profile/key identity, and old-envelope digest. Write a private sibling, flush, atomically publish with no-replace semantics, reopen/parse it, unwrap it through DPAPI if available, independently unwrap it through RecoveryWrapper, and compare its identity/digest to the old active envelope and journal. Publish and reopen-verify its separate authenticated `prepared_for_retention` metadata the same way. Only then replace the journal with `retained_n_published`.
7. Atomically replace the active envelope with the pending N+1 envelope (changing its state to `active`), reopen and unwrap-verify it, atomically finalize retained N metadata to `retained_for_read` with `retired_for_write_at`, then replace the journal with `envelope_n_plus_1_promoted`.
8. Replace the journal with `rotation_complete`, then flush/removal attempt. A stale `rotation_complete` journal is parsed and deterministically retired; it is never ignored. Remove `previous-N.sqlite` only after this complete state is reconciled and it is no longer required for crash recovery.

Thus an N+1 active database is never activated without a durably published N+1 recovery path in the journal, and active envelope N is never replaced until the retained N protected material required by retention policy is atomically published and reopen-verified. The last durable protected VMK(N) cannot disappear at promotion: retained N already exists and authenticates the N-authenticated journal after promotion.

## State machine and restart recovery

| Logical state | Active DB / key | active and pending material | Writes | deterministic startup/recovery |
|---|---|---|---|---|
| `ACTIVE_N` | `vault.sqlite`, Kdb(N) | active N; no journal | normal | validate N and open |
| `PREPARING_N_PLUS_1` | N | active N; un-published memory/staging only | none | discard un-published private staging; open N |
| `ROTATION_PENDING` | N | active N + `prepared` journal/pending N+1 | none | authenticate with N; discard candidate if absent/unverified; resume or roll back to N |
| `VERIFYING_N_PLUS_1` | N | active N + `candidate_verified` journal | none | verify candidate N+1 again; resume activation or delete candidate and use N |
| `ACTIVATING_N_PLUS_1` | N or N+1 | active N + `activation_started` journal | none | controlled open of active DB under Kdb(N), then Kdb(N+1); exactly one valid result selects rollback/resume |
| `DB_N_PLUS_1_VERIFIED` | N+1 | active N + `db_n_plus_1_verified` journal | none | publish/reopen-verify retained N, then continue; active N authenticates journal |
| `RETAINED_N_PUBLISHED` | N+1 | active N + retained N + `retained_n_published` journal | none | promote active envelope N+1; both active and retained N authenticate journal |
| `ENVELOPE_N_PLUS_1_PROMOTED` | N+1 | active N+1 + retained N + `envelope_n_plus_1_promoted` journal | none | authenticate journal with retained N, finalize metadata, and retire journal |
| `ROTATION_COMPLETE` | N+1 | active N+1 + retained N + stale `rotation_complete` journal or none | normal only after journal is retired | deterministically retire journal; active writes use N+1 only |
| `RETAINED_N_FOR_OLD_BACKUP_READ` | N+1 | active N+1 + immutable retained N envelope | N+1 only | old backup may unwrap N and restore isolated; active writes reject N |
| `RETIRED_N` | N+1 | active N+1; N retained file destroyed | N+1 only | N backups are expired/unrecoverable by declared policy; no reconstruction |

Fault handling is deterministic: before N+1 generation, discard no durable state; after pending envelope/journal publication, use N after authenticating the journal; during/after export or before verification, retain N and discard only the unverified candidate; after candidate verification but before activation, reverify or roll back to N; during activation, controlled dual-key validation decides whether N remains active or N+1 must be resumed; after DB activation but before retained publication, active N and journal authenticate recovery and startup retries retained publication; during retained publication, active N/journal remain and startup retries it; after retained verification but before promotion, active N + retained N + journal + verified N+1 resume promotion; immediately after promotion, active N+1 reopens while retained N authenticates the journal, then cleanup resumes; after stage update before deletion, both envelopes remain valid and stale journal retirement is deterministic. A kill/reboot at each point follows that same durable-stage rule. Startup never generates a replacement VMK, overwrites an envelope, creates an empty DB, guesses a version, or treats a candidate as active.

The controlled dual-key probe opens only the named active DB using the two protected candidate keys from a valid journal, runs `cipher_integrity_check`, `integrity_check`, `foreign_key_check`, and the fixed vault/profile identity query. It does not inspect user content as an oracle. Exactly one key must validate and agree with the stage. Both valid, neither valid, a journal/envelope digest mismatch, missing required old/pending material, or a database identity mismatch is `ROTATION_RECOVERY_FAILED_CLOSED`; no Personal content is exposed. Before promotion, active N authenticates the journal. After promotion, startup authenticates every stale transition journal through the reopen-verified retained N envelope; it never requires active N+1 to decrypt a journal under N. Missing or invalid retained N after promotion is `ROTATION_RECOVERY_FAILED_CLOSED`, never an ignore/delete shortcut. If DPAPI is unavailable while a journal exists, recovery requires the supplied recovery secret: unwrap active/retained N, authenticate the journal, unwrap pending N+1 where needed, then execute the same controlled state machine. Without a valid recovery secret it fails closed; it does not restore/activate bytes opportunistically.

## Historical backup keys and retirement

Each Personal backup records its `key_version`, four salts, and recovery header in its authenticated bootstrap. The active envelope serves only its current version. The immutable retained envelope contains exactly format/version, vault/profile IDs, key version, four salts, DPAPI wrap, RecoveryWrapper, and the original N envelope digest; it contains no lifecycle state or dates and therefore never falsely claims N was retired while N is still active. The separate content-free `PMV1-RETAINED-KEY-METADATA-V1` file has exact fields `format`, `version`, `vault_id`, `profile_id`, `key_version`, `retained_envelope_sha256`, `state`, `created_at`, `active_from`, `retired_for_write_at`, `retained_for_read_until`, `auth_nonce_hex`, and `auth_ciphertext_hex`. It is AES-GCM authenticated under Kmanifest(N), rejects unknown/duplicate fields, and progresses atomically from `prepared_for_retention` (where `retired_for_write_at` is JSON `null`) before promotion to `retained_for_read` only after promotion (where it is the actual retirement time). Destruction removes this metadata with its retained envelope and is represented only by a separate non-secret receipt. The envelope is immutable, ACL-restricted, excluded from active-write key resolution, and found solely by the bootstrap version under `retained-keys`.

Before rotation, N has a verified backup; N's `retained_for_read_until` is the maximum declared expiry of every valid N backup, including a minimum retention horizon recorded by policy. Deletion and backup expiry recompute that maximum. Destruction is permitted only when every N backup is expired/deleted and no active DB, journal, staging recovery, or restoration depends on N. It removes the retained envelope and associated key metadata, records only a content-free receipt, and never accumulates keys indefinitely. Attempts to destroy a required N key or use it for active writes fail closed. Restoring N always decrypts into isolated Personal staging and needs explicit owner activation; it cannot overwrite active N+1.

## Recovery bootstrap wire format

`PMV1-RECOVERY-BOOTSTRAP-V1` is bounded UTF-8 canonical JSON, maximum 32 KiB, adjacent to—not inside—the encrypted payload. Exact top-level fields are `format`, `version`, `vault_id`, `profile_id`, `profile_version`, `key_version`, `db_salt_hex`, `backup_salt_hex`, `export_salt_hex`, `manifest_salt_hex`, `recovery`, `backup_id`, `payload_nonce_hex`, `payload_length`, `payload_sha256_hex`, and `bootstrap_auth`. `bootstrap_auth` has exactly `nonce_hex` (12 bytes) and `ciphertext_tag_hex` (16 bytes). The `recovery` object is exactly the bounded `RecoveryWrapHeader`. No unknown/duplicate fields are allowed at either level. IDs and hex use the active-envelope bounds; `payload_length` is a positive bounded integer set by the package maximum; invalid hex, overlong strings, and any Argon2 value outside existing bounds are rejected before KDF allocation.

After recovery-secret unwrap, derive Kmanifest with this bootstrap's manifest salt. `bootstrap_auth` is AES-256-GCM encryption of an empty plaintext: nonce is `bootstrap_auth.nonce_hex`, ciphertext/tag is `ciphertext_tag_hex`, and AAD is `PMV1-RECOVERY-BOOTSTRAP-V1|` plus the canonical JSON bytes of every top-level field except `bootstrap_auth`. It authenticates the recovery header, vault/profile/key identity, all salts, backup ID, and payload descriptor. Kbackup then authenticates/decrypts the payload. Bootstrap A/payload B, N/N+1 mixing, changed backup ID/digest/length/profile/key/salt/recovery header, duplicate field, unknown field, overlength, invalid hex, or excessive Argon2 parameters fail before staging activation; malformed bounds fail before KDF, bootstrap changes fail at manifest authentication, and payload changes fail at payload authentication/digest comparison.

## Required future proof

RDG-02 must separately prove independent recovery, active rotation, interrupted rotation recovery, old-backup restore after rotation, and retired-key destruction after retention. Fault injection is required after pending envelope, after journal, during export, after candidate creation, after DB activation before retained publication, during retained publication, after retained publication before envelope promotion, immediately after envelope promotion, and before journal cleanup; each restarts and asserts recoverable VMK(N)/VMK(N+1), matching active DB key, no ambiguous key state, and no data loss. RDG-03 repeats those publication barriers for backup N → active N+1 → restart → isolated N restore using retained N and a recovery secret. Self-falsification additionally covers corrupt/missing journal or envelopes, both/neither key valid, stale journal, wrong recovery secret, DPAPI loss, disk-full and file-lock activation failures, expired retention, and forbidden retained-key writes.
